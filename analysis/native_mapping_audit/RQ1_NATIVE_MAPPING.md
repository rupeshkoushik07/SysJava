## 2. How each tool finds and maps native methods

### 2.1 Finding native methods (shared by both tools)

`PrototypeFinal.java` (EchoTrace/SysJava bytecode stage) scans the JARs observed during the
startup trace (`Dataset/JARFILES_*`) and the container's JDK runtime (`Dataset/RUNTIME_*`). It
records every method with `ACC_NATIVE` (ASM) / `MethodModifier.NATIVE` (SootUp) as
`fully.qualified.Class.method`. Output: `Bytecode_Analysis/outputs_<app>/native_methods.txt`.

**Both tools were run on this same file**, so the comparison has an identical denominator.

### 2.2 SysJava mapper — `EchoTrace/scripts/mapped_updated.py`

Each name is resolved by the first rule that matches, in this order. The tag is written to
`mapped_method_syscalls.txt`.

| Order | Tag | Evidence | Automatic? |
|---|---|---|---|
| 0 | `PLATFORM_EXCLUDED` | keyword list (`.win32.`, `.kqueue.`, `Darwin`, `WindowsTerminal`, …) | curated list |
| 0 | `INTRINSIC` | `intrinsic_whitelist_all_jdks.txt` | curated list |
| 1 | `JNI` | `nm` export `Java_<mangled>` in a container `.so` | yes (binary) |
| 1.2 | `JNI_DYNAMIC` | third-party `RegisterNatives` tables (`extract_jni_bindings.py` → `jni_dynamic_bindings.txt`) | yes (binary) |
| 1.3–1.5 | `NETTY` | `nm` fallback on `netty_<module>_<class>_<method>` names | yes (name pattern) |
| 2 | `JVM` | libjvm `RegisterNatives` tables (`extract_registernatives_binary.py` → `jvm_dynamic_mapping.txt`), source fallback | yes (binary) |
| 2.5 | `JVM_BUILTIN` | hard-coded `JVM_BUILTIN_NATIVES` (`Object.*`, `System.*`) | hand-written |
| 3 | `REGISTERED` | same libjvm table as `JVM`, non-`JVM_*` targets (`Unsafe_*`, `jfr_*`, `MHN_*`, …) | yes (binary) |
| — | `DIRECT_LIBC_BRIDGE` | hard-coded `DIRECT_LIBC_METHODS` (JNA direct mapping to libc) | hand-written |
| — | `SIGAR_LIST_BRIDGE` | hard-coded `SIGAR_LIST_BRIDGES` | hand-written |
| — | `NOT_FOUND_IN_LIBS`, `REGISTERED? UNRESOLVED` | — | — |

This answers the reviewer's request to "separate automatic binary recovery from any source or
manual mappings". In this dataset the hand-written rules produce 22 mappings (8 `JVM_BUILTIN`,
9 libc bridge, 5 SIGAR); the curated lists produce 192 platform and 37 intrinsic labels.

### 2.3 SWAT4J mapper

* **Upstream** (`Tutorial/swat4j/upstream/binary_analyser.py`) does three things:
  * Builds `Java_*` maps by running `objdump`/`nm` on a fixed list of libraries (host JDK,
    hard-coded `libnetty`, `libjffi`, `libtcnative`, `libsigar` paths).
  * Turns each symbol into a dotted name with `replace('_','.')`.
  * Reads `JVM_*` targets from OpenJDK source `JNINativeMethod` tables. For `io.netty.*` it takes
    the first `netty*` symbol whose name `endswith(method)`.
* **The port we ran** (`Prototype/swat4j_mapping.py`) keeps that logic. It points the scans at the
  container's extracted `LIBS_*` directory instead of hard-coded paths. It still scans the
  **host** JDK 8 (`/usr/lib/jvm/java-8-openjdk-amd64`, 37 libs) and uses JDK 8 source for `JVM_*`,
  as upstream does. It applies the same intrinsic whitelist as SysJava.
* Per-method output: `swat4j_mapped_methods.txt`, `swat4j_unmapped_methods.txt`,
  `swat4j_intrinsic_methods.txt`, `swat4j_summary.txt` next to `native_methods.txt`.
* **OrientDB had no per-method SWAT4J output.** It was regenerated into `swat4j_rerun_orientdb/`.
  The host JDK 8 is no longer installed, so this run used the container's own JDK 8 libs. Its
  `Java_XXX` = 284 matches the earlier full log (`Final_results_swat4j_full_logs`).

Structural limits of SWAT4J, visible in the data:

* **No `RegisterNatives` recovery.** `Unsafe_*`, `jfr_*`, `MHN_*` and Netty registrations are only
  found when the name pattern happens to match.
* **Lossy dotted-name keys.** `_1`/`_00024`/`__sig` names never match, so it finds 0 "partial" JNI
  names.
* **Suffix heuristic picks wrong functions** (§6.4).

## 3. Denominator definition (proposed text for §V.A "Measurements")

> **Denominator.** For each image, the denominator is the set of distinct `(class, method-name)`
> pairs that carry `ACC_NATIVE` in the analysed bytecode: the JARs opened during the startup trace
> plus the container's JDK runtime. Overloads of one name count once. A name is *mapped* when the
> tool emits at least one native function in a library present in the image. It is *accounted for*
> when it is mapped, or classified as platform-excluded (a non-Linux API) or as a JVM intrinsic.
> Everything else is *not found*. JNA and FFI/FFM bindings without `native` declarations are
> reported separately. Both tools are evaluated on the identical name list for each image.

## 6. Automatic validation (exhaustive, every mapping)

These checks need no human judgement and run on all 5,198 SysJava and 3,850 SWAT4J mappings
(`audit_native_mapping.py`, `collect_sample_evidence.py`, `platform_check.py`).

| Check | How | SysJava result |
|---|---|---|
| Symbol exists in the claimed library | `nm -D` / `nm` on the container `.so` | fails only for 6 libc bridges (§6.3) |
| `Java_` name encodes the method | re-mangle `class.method` per the JNI spec; compare | 3,334 / 3,334 pass |
| JNI long-name overload | decode `__<sig>`; compare with descriptor read from the container's class file | 97 / 99 pass; 2 jffi `getZeroTerminatedByteArray__JJ` match no declaration (JAR/lib skew) |
| Table-backed (RegisterNatives) pair present in recovered table | `(java method, symbol)` ∈ `jvm_dynamic_mapping.txt` ∪ `jni_dynamic_bindings.txt` (shaded Netty normalised) | all except 9 cross-class Netty aliases and 3 Tomcat `System.*` (registered by libjava's `System.c`; correct) |
| Table-backed signature matches a Java declaration | table signature vs class-file descriptor | **62 / 1,745 mismatch** (§6.1) |
| Netty name tokens | `netty_<module>_<class>_<method>` matches class and method | 88 / 88 pass |
| Platform exclusion really non-Linux | search all image `.so` files for the exact `Java_` symbol | **13 / 192 wrong** (§6.2) |

### 6.1 Wrong RegisterNatives overload (62 mappings, SysJava)

`registered_method_map` is keyed by name only and keeps the first table row. JDK 8's `unsafe.cpp`
registers both the 1.4-era `int`-offset entries and the current `long`-offset ones, so the legacy
row wins for:

`Unsafe.getObject`→`Unsafe_GetObject140`, `putObject`→`Unsafe_SetObject140`,
`getBoolean`→`Unsafe_GetBoolean140`, `putBoolean`→`Unsafe_SetBoolean140`,
`staticFieldBase`→`Unsafe_StaticFieldBaseFromClass`, `defineClass`→`Unsafe_DefineClass0`,
`copyMemory`→`Unsafe_CopyMemory (JJJ)V`, `setMemory`→`Unsafe_SetMemory (JJB)V`.

None of these signatures exists in the JDK 8 `sun.misc.Unsafe` class file. That gives 6–8 per JDK 8
app, plus 2 Solr version-skew rows (`jfr_add_string_constant`, `MHN_resolve_Mem`).
Full list: `out/overload_mismatches.csv`.

* **Syscall impact:** probably small. The correct sibling (`Unsafe_GetObject`, …) is a
  non-syscall accessor in the same library. The mapping is still wrong and must be reported.
* **Fix:** key `registered_method_map` by `(class, name, signature)` and emit every row whose
  signature matches a declared overload.

### 6.2 Wrong platform exclusions (13, SysJava)

The keyword rules exclude:

* Groovy: `org.fusesource.jansi.internal.Kernel32.init` and its 10 `Kernel32$*.init` struct
  initialisers.
* Cassandra: `org.hyperic.sigar.win32.FileVersion.gather` and `Win32.findExecutable`.

The Linux `libjansi.so` and `libsigar-amd64-linux.so` export exactly these `Java_` symbols, so the
methods are callable on Linux. List: `out/platform_exclusion_errors.csv`. The other 179 exclusions
have no Linux symbol anywhere in the image.

### 6.3 Wrong library for libc bridges (6, SysJava)

Cassandra's `NativeLibraryLinux` (JNA direct mapping) maps `getpid`, `fcntl`, `open`, `close`,
`fsync`, `strerror` to the right libc functions. However, it records the owner as `libjvm.so`,
which does not define them. The other 3 (`mlockall`, `munlockall`, `posix_fadvise`) correctly name
`libc.so.6`. Because SysPart roots are per library, these 6 functions are not rooted in libc.

### 6.4 SWAT4J incorrect mappings

The `endswith` Netty heuristic picks unrelated functions:

* `io.netty.channel.unix.Socket.connect` → `netty_unix_socket_disconnect` (Storm, Solr)
* `io.netty.channel.unix.FileDescriptor.open` → `netty_epoll_native_isSupportingTcpFastopen` (Storm)

Both tools map `epoll.NativeStaticallyReferencedJniMethods.{ssizeMax,iovMax,uioMaxIov}` to
`netty_unix_limits_*` (newer Netty moved them to `unix.LimitsStaticallyReferencedJniMethods`). That
is the same constant-returning function under a different registered class: approximate, no
syscalls. SWAT4J's `Java_XXX` mappings all pass the name check; it simply never produces escaped or
overloaded names.

### 6.5 Missed targets (false negatives)

* **Cassandra:** SysJava reports 4 Netty methods (`NativeStaticallyReferencedJniMethods.{ssizeMax,
  iovMax, uioMaxIov}`, `unix.Socket.getPeerCredentials`) as not found. The old
  `libnetty-transport-native-epoll.so` does export matching `netty_*` symbols; SWAT4J finds them.
* **JFR:** `jdk.jfr.internal.JVM.getClassId` is whitelisted as intrinsic, but Cassandra's libjvm
  defines `jfr_class_id` and the registration string `getClassId` (§7).

## 7. Manual validation of a stratified sample of additional mappings

**Population.** "Additional" = names SysJava accounts for that SWAT4J does not (1,544 across the ten
images). **Strata** = SysJava resolution category. **Second-level strata** = application,
allocated proportionally, at least one per app. Seed `20261104`; sizes in
`audit_native_mapping.py:STRATUM_SIZE` (RegisterNatives, the paper's main claim, gets the largest
sample; strata of ≤30 are reviewed exhaustively).

**Procedure (per row; evidence columns in `out/validation_sample_evidence.csv`):**

1. Read the Java declaration's descriptor(s) from the class file in the container's own JAR
   (`java_native_descriptors`). Confirm the method is `native` and count its overloads.
2. Confirm the claimed function is defined in the claimed container library (`nm`).
3. For RegisterNatives rows: find the recovered `JNINativeMethod` row(s) for this method
   (`table_rows`) and check that the chosen target's signature equals a declared descriptor
   (`signature_match`). For JNI long names: decode `__<sig>` and compare the same way.
4. Check whether the library was opened during the startup trace (`lib_loaded_at_runtime`).
5. For platform rows: search every `.so` in the image for the exact `Java_` symbol.
6. For hand-written rules and intrinsic labels: consult JDK 8 sources
   (`swat4j/jdk8u-src/jdk/src/share/native/java/lang/{System,Object,Class}.c`) and the libjvm
   symbol table.
7. Assign one verdict and record the evidence (`out/validation_sample_adjudicated.csv`; the rules
   applied are in `adjudicate_sample.py`, the three judgement calls in `MANUAL_DECISIONS`).

Verdicts: **correct**; **correct_partial** (implements one overload; others omitted);
**approximate** (no exact target exists; a related function was used); **incorrect_symbol**;
**incorrect_library**; **misclassified**.

**Results** (`out/validation_summary.csv`)

| Stratum | Population | Sampled | Correct | Correct (1 of N overloads) | Approx. | Incorrect symbol | Incorrect library | Misclassified |
|---|---|---|---|---|---|---|---|---|
| RegisterNatives (`REGISTERED`/`JVM`/`JNI_DYNAMIC`) | 1,084 | 59 | 44 | 8 | 0 | 7 | 0 | 0 |
| JNI partial (`_1`/`_00024`/`__sig`) | 235 | 25 | 14 | 11 | 0 | 0 | 0 | 0 |
| JNI exact (libs SWAT4J did not scan) | 14 | 14 | 14 | 0 | 0 | 0 | 0 | 0 |
| Netty name pattern | 5 | 5 | 5 | 0 | 0 | 0 | 0 | 0 |
| Hand-written rules | 14 | 14 | 3 | 0 | 5 | 0 | 6 | 0 |

| **Total** | **1,544** | **140** | **98** | **19** | **5** | **7** | **6** | **5** |

Reading the sample alongside the exhaustive checks:

* **RegisterNatives.** 52/59 sampled correct (88%, Wilson 95% CI 77–94%). The exhaustive overload
  check puts the true error rate in this stratum at **62/1,084 = 5.7%**; the sample over-drew
  `sun.misc.Unsafe`. All errors are the §6.1 legacy-overload bug. Every sampled target was in the
  recovered table and defined in the claimed library.
* **JNI partial and exact.** 39/39 correct. 11 implement one of several overloads. The 14 "exact"
  rows are Hadoop erasure-code natives in `hadoop-3.3.6/lib/native/libhadoop.so`; SWAT4J only scans
  top-level `.so` files.
* **Hand-written rules.**
  * 3 libc bridges correct; 6 wrong library (§6.3).
  * 5 SIGAR `X.gather` → `Sigar_getXList` bridges are approximate: libsigar exports no `Java_`
    symbol for `X.gather`, so the method could never be called; the list native that populates
    these objects was used instead. Report them as heuristics, not recovered bindings.
* **Platform.** 18/20 correct; 2 jansi `Kernel32$*.init` are exported on Linux. The exhaustive
  check finds 13/192 overall (§6.2).
* **Intrinsic.** All 3 wrong. `getClassId` has a real target `jfr_class_id`;
  `setCompressedIntegers` and `registerNatives` have no target in this libjvm and should be not
  found. The same three JFR names make up 28 of the 37 intrinsic labels across the ten images. Of
  the rest, only `MethodHandle.invoke/invokeExact` (6) are genuine signature-polymorphic intrinsics.
  Hadoop `DomainSocket.write0`, `NativeIO$POSIX.getUIDforFDOwnerforOwner` and `sun.misc.Perf.attach`
  are not JIT intrinsics and need re-checking.
* **Library loading.** 47 sampled rows map into libraries present in the image but not opened
  during startup (Netty epoll in Storm, RocksDB, PKCS11, Hadoop). The mapping is correct; whether
  the library is used depends on workload. This links to the workload-validation TODO.

### Corrected resolution figures

Treating every confirmed error as "not mapped" (62 overload + 6 library + 2 jffi long-name + 5
approximate SIGAR, 13 platform + 28 JFR intrinsic as not accounted):

* SysJava mapped, confirmed correct or correct-partial: 5,198 − 75 = **5,123 / 5,551 (92.3%)**.
* Accounted after removing wrong labels: 5,427 − 75 − 13 − 28 = **5,311 / 5,551 (95.7%)**.
* SWAT4J mapped, excluding its 3 heuristic errors: **3,847 / 5,551 (69.3%)**.
